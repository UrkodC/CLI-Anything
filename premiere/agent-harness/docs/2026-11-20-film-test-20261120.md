# Field test on a real film: "The Monster Bridge" (2026-11-20)

First new film made in Premiere 27.0.0 (build 88) with the CLI in the pipeline, at commit c554f16.
Project: `/Volumes/Samsung 2TB/Videos Premiere/20261120/The Monster Bridge Claude.prproj`, sequence
"The Monster Bridge - Claude v1" (5415e967-1522-434e-9d46-48011cb25ec9), 11 shots, 3840x2160, 23.976, 56.3 s.
Split: MCP made the project, imported, made the sequence, trimmed audio, set audio keys, transitions, exports.
CLI placed shots, applied effects, set LUTs, grade values, level keys, and exported review frames.
Raw outputs: `Claude review/v1/cli_*.json` in the project folder.

## Findings for the CLI

1. `live effect set --from` refuses `--sequence-name` ("the plan file names the sequence"). Fine, but the
   other plan commands (`place`, `keys set`) take `--sequence-name` with a plan. Small inconsistency; the error
   message was clear and nothing was sent.
2. `--prove` frame time vs source time: the frame exported at sequence 32.0 s matched source 4.14-4.16 s of
   C2299, not 4.18 (clip start 27.8195). Premiere snaps the sequence time down to frame 767. Worth printing the
   frame number and the source time of the exported frame in the `--prove` output, so a follow-up ffmpeg check
   uses the same frame without a search.
3. `live lut set` is one clip per call. A `--clips 0,1,2` or `--all` form (one lease, one readback table) would
   save the shell loop. Each call took under 1 s, so this is convenience, not speed.
4. Audio is the gap for a film: crossfade trims (`trim_clip include_linked false`), Level keys and clip levels
   still go through MCP (31 calls in 2 messages here). A `live audio` plan command fed by the skill's
   `xfade_plan.py` output would remove the largest remaining MCP pass.
5. zsh users: pass repeated `--time` options as an array; a single string variable is not split (my error, not
   the CLI's; the CLI rejected it cleanly with "unexpected extra argument").
6. No CLI command caused a recovery, a dialog or a lease wait. One recovery came from an MCP `export_sequence`
   into a folder that did not exist (my error). `cli-anything-premiere recovery show` gave the clip counts and the
   revision in one short call, but the acknowledge still needs the MCP host-state revision, which only
   `inspect_operation_recovery` prints (the whole timeline). A `recovery show` that also prints the host-state
   revision would make the safe check cheap.
7. Later versions (v2 to v4) were audio and score changes only: all MCP (roll_edit, remove_keyframe_range,
   trim_clip, add_audio_keyframes, score swap). The CLI had nothing to do there, which matches finding 4.
8. v5 (after the critic): after an MCP `slip_edit` moved C2297's Rotation keys with the media, `live keys set` re-leveled
   it from a fresh level plan in one call (old keys replaced). `live effect set --from` with a `node_id` entry set one
   Saturation value. A plan entry with both `node_id` and `track`/`clip` is refused ("not both"): clear message.
   `live frame export` of 2 JPG frames was the quick check of a push-in before a full 4K export.
